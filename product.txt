## 1. Mission

Build a complete, runnable Agentic AI system in 5 days: backend first, then UI.

The project must teach and demonstrate:

1. Harness engineering
2. Agent loop engineering
3. Graph engineering
4. LLM fundamentals and structured outputs
5. RAG and hybrid retrieval
6. Tool calling and tool execution
7. LangChain and LangGraph
8. Observability using Langfuse and an optional LangSmith integration
9. Custom evaluation and regression testing
10. Cost and latency optimization
11. Quality, data, and retrieval drift monitoring
12. Security, reliability, testing, and deployment

13. Sandboxed workspace (filesystem + terminal) tooling with human-in-the-loop approval

Build the backend first and expose everything through REST APIs, OpenAPI documentation, automated tests, a CLI, and structured logs. Only after the backend passes its tests, build the web UI (Section 24) as a pure client of those same APIs; the UI must not contain business logic the API lacks.

Work in small, verifiable milestones. Implement actual working code, not just architecture documents or placeholder functions. Run tests after every major milestone, fix failures, and maintain a working README.

## 2. Product to Build

Build an intelligent research and knowledge agent called AgentOps AI.

Users can upload technical documents, ingest their contents, ask questions, retrieve evidence, execute approved tools, and receive answers with source citations.

Example request:

"Compare these two architecture documents, identify conflicting requirements, calculate the migration impact, verify your claims against the sources, and return an implementation plan."

The backend should be able to:

- Ingest and index documents.
- Retrieve relevant passages with metadata and source references.
- Decide whether a question needs retrieval, tools, or both.
- Execute tools through a controlled agent loop.
- Orchestrate multi-step workflows through a graph.
- Validate answers and citations.
- Record traces, token usage, cost, latency, and failures.
- Run evaluation datasets and detect regressions.
- Compare model and retrieval configurations.
- Enforce execution budgets, timeouts, and tool permissions.
- Expose operational and evaluation metrics through APIs.

Observability:

Testing and quality:

## 4. Core Architecture

Implement the following logical pipeline:

API request
  -> Authentication and request validation
  -> Request and execution budget initialization
  -> Agent harness
  -> LangGraph workflow
      -> Request classification
      -> Workflow planning
      -> Retrieval and/or tool execution
      -> Evidence validation
      -> Answer generation
      -> Citation and output validation
      -> Bounded retry or correction, if required
      -> Final response
  -> Trace and metrics finalization

Supporting systems:

- PostgreSQL: documents, chunks, metadata, sessions, executions, evaluation datasets, and results.
- pgvector: embeddings and vector search.
- Langfuse: LLM and workflow traces.
- Optional LangSmith: comparative tracing/evaluation adapter.
- Monitoring service: latency, cost, failures, quality, and drift signals.
- CLI: ingest documents, run queries, execute evaluations, and compare experiments.

Keep the LLM provider, embeddings, vector search, tools, observability, and evaluation implementations behind explicit interfaces where doing so improves testability.

Avoid unnecessary abstractions. Prefer readable, typed code.

## 5. Harness Engineering

Create a central execution harness responsible for controlling agent execution.

Implement these responsibilities:

### Execution context

Define a typed execution context containing:

- Request ID and execution ID.
- User or tenant identifier where applicable.
- Current workflow state.
- Request deadline.
- Maximum model calls.
- Maximum agent steps.
- Maximum tool calls.
- Maximum retries.
- Token or monetary budget.
- Allowed tools and permissions.
- Cancellation status.
- Collected trace identifiers.
- Accumulated usage and cost.

### Policy enforcement

Before each model call or tool call:

- Check cancellation and deadline.
- Check the relevant execution budget.
- Validate tool permissions.
- Validate and normalize tool arguments.
- Enforce per-tool timeouts.
- Record the attempted operation.
- Reject execution when the budget is exhausted.

Do not trust the model to enforce these policies itself.

### Context management

Implement:

- Bounded conversation history.
- Relevant document context selection.
- Duplicate passage removal.
- Context size limits.
- Explicit separation between system instructions, user input, tool output, and untrusted document content.
- Truncation or summarization policies where needed.

### Output validation

Validate model outputs against Pydantic schemas when structured output is required.

For failed validation, allow a small bounded correction attempt. Never create an infinite repair loop.

### Failure handling

Define typed errors for:

- Provider errors.
- Rate limits.
- Timeouts.
- Invalid tool arguments.
- Tool execution failures.
- Budget exhaustion.
- Invalid model output.
- Retrieval failures.
- Verification failures.

Retry only transient and safe failures. Use bounded exponential backoff with jitter for eligible retries.

Do not blindly retry non-idempotent operations.

### Required demonstration

Create tests proving that:

- A tool cannot execute without permission.
- The harness stops at the step limit.
- The harness stops at the deadline.
- The harness stops when its budget is exhausted.
- Malformed tool arguments are rejected.
- Cancellation prevents subsequent operations.
- Retries cannot continue indefinitely.

## 6. Agent Loop Engineering

Implement a custom agent loop before introducing LangGraph orchestration.

The loop should follow this sequence:

1. Build a bounded model input.
2. Invoke the model.
3. Record usage, latency, and the model response.
4. Validate the response.
5. If the response is final, validate and return it.
6. If the response requests a tool, validate the tool name and arguments.
7. Ask the harness for permission to execute it.
8. Execute the tool with a timeout.
9. Append the tool result to the execution state.
10. Repeat until completion, cancellation, failure, or a configured limit.

Create a typed model response contract with explicit outcomes such as:

- FINAL
- TOOL_CALLS

Use the provider's supported structured-output or tool-calling API. Do not parse arbitrary natural-language text as executable instructions.

Implement:

- A maximum of 8 agent steps by default.
- A configurable model-call limit.
- A configurable tool-call limit.
- A configurable deadline.
- A configurable cost budget.
- A maximum of 2 correction attempts per eligible failure.
- An execution ledger recording model calls, tools, results, and failures.

Make limits configurable; these values are initial defaults, not universal production settings.

Implement three tools initially:

1. document_search(query, filters)
2. calculator(expression)
3. document_metadata(document_id)

The calculator must use a safe, restricted expression evaluator. Do not use unrestricted eval.

The metadata tool must enforce document ownership and access control.

The document search tool must use the retrieval subsystem rather than inventing document contents.

Write unit tests for normal completion, multiple tool calls, repeated tool-call loops, invalid arguments, tool failure, timeout, cancellation, and budget exhaustion.

## 7. Graph Engineering With LangGraph

After the custom loop works, implement the main agent workflow in LangGraph.

Define a typed graph state containing:

- Request and execution IDs.
- Original user question.
- Classified intent.
- Plan.
- Retrieved passages.
- Tool results.
- Draft answer.
- Citation records.
- Validation findings.
- Execution budget and counters.
- Errors and retry count.
- Final answer and completion status.

Build these nodes:

1. classify_request
2. plan_workflow
3. retrieve_evidence
4. select_or_execute_tools
5. generate_answer
6. validate_citations
7. verify_answer
8. retry_or_revise
9. human_approval
10. finalize_execution

Create conditional edges for:

- Retrieval required versus not required.
- Tool execution required versus not required.
- Successful verification versus bounded correction.
- Recoverable failure versus terminal failure.
- Human approval required versus automatic continuation.

Use explicit stop conditions and enforce budgets through the harness, not just graph prompts.

Add checkpointing with a supported LangGraph checkpointer. Persist resumable state where practical, but avoid persisting secrets or unnecessary sensitive content.

Use human approval for any future write-capable or externally consequential tools. The initial calculator, metadata lookup, and document search tools should be read-only.

Document when to use a graph, when a simple function pipeline is enough, and when a bounded agent loop is appropriate.

Do not implement multiple autonomous agents merely to make the project look advanced. First make one agent and one graph reliable.

## 8. RAG Engineering

Implement document ingestion and retrieval as a separate subsystem.

### Ingestion pipeline

Support at least:

- TXT.
- Markdown.
- PDF with text extraction.
- Explicit document metadata and ownership.

Pipeline:

Upload
  -> File validation
  -> Size and type limits
  -> Text extraction
  -> Normalization
  -> Chunking
  -> Embedding generation
  -> PostgreSQL and pgvector storage
  -> Ingestion status update

Store:

- Document ID.
- Document version.
- Tenant or owner ID.
- File name and content hash.
- Page number or source location when available.
- Chunk index.
- Chunk text.
- Embedding model and version.
- Ingestion status and timestamps.

Make ingestion idempotent using content hashes and versioning.

Never silently mark partially failed ingestion as successful.

### Chunking

Implement a configurable chunker with:

- Target chunk size.
- Overlap.
- Stable chunk identifiers.
- Source metadata preservation.
- Document boundary preservation where practical.

Avoid splitting every document using the same arbitrary strategy without testing alternatives.

### Retrieval

Implement:

1. Vector retrieval.
2. PostgreSQL full-text retrieval.
3. Hybrid ranking using Reciprocal Rank Fusion.
4. Metadata filtering and tenant isolation.
5. Duplicate chunk removal.
6. Optional reranking through an interface.

Return structured retrieval results containing chunk IDs, document IDs, text, page/source metadata, and scores.

### Answer grounding

The answer generator must receive the retrieved evidence explicitly.

Citations must refer to actual retrieved sources. Validate that each cited chunk or source exists and belongs to the authorized document set.

When evidence is insufficient, the system must say so rather than inventing facts.

### RAG evaluation

Measure:

- Recall@k.
- Mean Reciprocal Rank.
- Hit rate.
- Context relevance.
- Citation validity.
- Answer groundedness.
- Answer correctness on questions with reference answers.

Create tests for empty documents, duplicate ingestion, missing embeddings, unauthorized documents, irrelevant retrieval, and unsupported questions.

## 9. Tool System and MCP Extension

Define a common tool interface with:

- Name and description.
- Pydantic input schema.
- Output schema.
- Permission requirements.
- Timeout.
- Idempotency characteristics.
- Execution function.
- Error mapping.

Create a tool registry and allowlist.

The model may request a tool, but only the harness can authorize and execute it.

Add an optional MCP adapter after the local tool registry works. Demonstrate how MCP standardizes tool discovery and invocation, while retaining the same authorization and budget controls.

Do not expose UNRESTRICTED shell execution, arbitrary Python execution, or unrestricted network requests to the agent. Workspace access (9.1) is the only exception, and it is restricted in code.

Treat tool outputs and retrieved documents as untrusted data.

### 9.1 Sandboxed workspace tools (terminal + filesystem)

The agent can operate on exactly one configured directory, WORKSPACE_ROOT (per tenant:
WORKSPACE_ROOT/<tenant_id>/ or an explicitly registered directory). Tools:

- workspace_list(path)                   read-only
- workspace_read(path, max_bytes)        read-only
- workspace_search(pattern, glob)        read-only (grep-like, implemented in Python, no shell)
- workspace_write(path, content)         WRITE  -> requires human approval
- workspace_edit(path, old, new)         WRITE  -> requires human approval
- workspace_exec(argv)                   EXEC   -> allowlisted commands only; approval required
                                                 unless the command is on the read-only allowlist

Enforcement in code (never in the prompt):

- Path jail: resolve every path with realpath; reject anything outside WORKSPACE_ROOT, including
  via "..", absolute paths, and symlinks that escape the root.
- Deny-list of sensitive names even inside the root: .env, .git/config, *.pem, id_rsa*, .ssh/.
- Commands run with argv (no shell=True, no pipes, no globbing, no command substitution),
  cwd fixed to the workspace, a scrubbed environment (no API keys), a timeout, and an output cap.
- Command allowlist split into read-only (ls, cat, head, tail, wc, grep, find, git status,
  git diff, git log, pytest --collect-only) and write/exec (python -m pytest, git add, mkdir,
  etc.); write/exec commands go through the LangGraph human_approval node (interrupt/resume).
- Write size limits, binary-file rejection, and an audit record in execution_events for every
  attempted and executed operation, including rejections.
- The UI terminal panel (Section 24) executes through the SAME executor and policy; it is not a
  raw PTY.

Tests must prove: path traversal is rejected, symlink escape is rejected, non-allowlisted
commands are rejected, writes block until approved, rejected approvals perform no write, and
secrets are not present in the command environment.

## 12. Cost and Latency Optimization

Implement a usage and cost accounting layer.

Track per request:

- Model calls.
- Input and output tokens.
- Embedding calls.
- Tool calls.
- Retries.
- Estimated provider cost.
- End-to-end latency.
- Cost per successful task.

Keep provider pricing configurable and versioned. If pricing is unknown, label cost as unavailable rather than fabricating an amount.

Local Ollama models have no per-token price. Record their monetary cost as 0 with pricing source
"local", and still track tokens and latency (on local hardware, latency and tokens are the real
cost). Optionally compute a "hosted-equivalent cost" from a configurable reference price table,
clearly labelled as a hypothetical comparison.

Implement these optimizations incrementally:

1. Remove redundant model calls.
2. Reduce duplicate and irrelevant retrieved chunks.
3. Bound the conversation history and context size.
4. Route simple tasks to a cheaper model and complex tasks to a stronger model.
5. Cache deterministic tool results.
6. Add safe embedding or retrieval caching.
7. Add optional semantic caching with conservative similarity thresholds and permission-aware cache keys.

Cache keys must include relevant tenant, authorization, document version, model, and configuration information.

Do not cache sensitive responses across users. Define expiration and invalidation rules.

Benchmark the baseline against optimized configurations using the same dataset.

Report:

- Cost per request.
- Cost per successful task.
- p50 and p95 latency.
- Success rate.
- Quality score.
- Model calls and tool calls per request.

Optimization is successful only when the measured cost or latency improves without unacceptable quality loss.

## 13. Drift and Operational Monitoring

Implement a simple custom monitoring subsystem.

### Quality drift

Compare evaluation scores over time and against a stored baseline.

### Retrieval drift

Track retrieval recall, hit rate, source distribution, and ranking metrics across dataset and configuration versions.

### Data drift

Track document ingestion failures, corpus changes, metadata distributions, and changes in the question dataset where appropriate.

### Operational drift

Track latency, timeout rates, provider errors, retry rates, token usage, and cost per successful task.

Implement:

- Configurable thresholds.
- Evaluation run history.
- Baseline comparison.
- Alert records.
- An API to query monitoring results.
- A CLI command to run drift checks.

Start with a deterministic threshold-based detector. Add statistical methods only when justified by the collected data.

Create a regression demonstration: intentionally degrade chunking or retrieval configuration, rerun the golden dataset, and show the system detecting the decline.

Distinguish a real measured drift signal from an unverified suspicion.

## 16. Security Requirements

Implement:

- Input validation and upload size limits.
- File type validation.
- SQL parameterization through safe ORM/query practices.
- Authentication and document ownership enforcement.
- Tenant isolation in retrieval and cache keys.
- Tool allowlisting and permission checks.
- Per-request timeouts and budgets.
- Rate limiting or an explicitly documented development-only alternative.
- Secret management through environment variables.
- Safe error messages.
- Prompt-injection tests.
- Redaction of sensitive logs and traces.

For this learning project, use only synthetic or non-sensitive documents. Document tools are read-only; workspace write/exec tools are allowed only under the Section 9.1 controls, against a disposable directory, never your home directory or a real repository without a backup.

## 19. Engineering Workflow

Follow this sequence throughout development:

1. Inspect the existing repository before modifying it.
2. Produce a concise implementation plan and identify dependencies.
3. Implement one milestone at a time.
4. Write tests alongside each important component.
5. Run formatting, linting, type checks where practical, and relevant tests.
6. Fix actual failures before moving to the next milestone.
7. Update documentation and configuration examples.
8. Record architectural decisions and trade-offs.
9. Keep the repository runnable after every milestone.
10. Avoid unnecessary rewrites of already working components.

Use environment variables for configuration. Provide safe defaults for development and fail clearly when a required production setting is missing.

## 22. Recorder Agent (runs after every milestone)

After each milestone is implemented AND its tests pass, trigger a separate Recorder agent. It reads
the code and test output produced by that milestone (not the plan) and writes:

1. docs/journal/<NN>-<milestone>.md — what was built, files touched, key design decisions,
   trade-offs taken and rejected, commands to run it, test results, known limitations.
2. docs/interview/<NN>-<milestone>.md — interview questions WITH answers grounded in this code:
   - Basic: definitions and "what does X do" (8-10 questions)
   - Logical: "why", ordering, edge cases, what breaks if removed (8-10)
   - Advanced: scale, failure modes, production concerns (6-8)
   - Scenario: "a user reports...", "at 10x traffic..." with a worked answer (4-6)
   - Trade-off: option A vs B, what was chosen here and why, when the other wins (3-5)
   - Justification: defend a specific decision in this codebase against a skeptic (3-5)
   - System design: how this component fits the whole, scaling and evolution path (2-3)
   Every answer must reference real files/functions; no invented behaviour.

The Recorder only writes under docs/; it never edits source code.

## 23. Local Models (Ollama) — hardware-fit selection

Target machine: Apple M4, 16 GB unified memory, 10 cores. Budget roughly 8-9 GB for models so
Postgres, the API, the UI dev server, and the OS have headroom.

| Role                         | Model              | Approx size (Q4) | Why                                   |
|------------------------------|--------------------|------------------|---------------------------------------|
| Main agent / answer / tools  | qwen3:8b           | ~5.2 GB          | Native tool calling + JSON schema     |
|                              |                    |                  | output in Ollama; strong reasoning    |
| Router / classifier / cheap  | qwen3:1.7b         | ~1.4 GB          | Fast; used for classification and     |
|                              |                    |                  | the "cheap model" routing experiment  |
| Embeddings                   | nomic-embed-text   | ~0.3 GB          | 768-dim, 8k context, well supported   |

Fallbacks: llama3.1:8b (main) and llama3.2:3b (router) if qwen3 underperforms on the eval set.
Not recommended on 16 GB: 14B+ models (swap pressure makes latency unusable alongside Docker).
Disable qwen3 "thinking" mode for structured outputs (think=false) to save tokens and latency;
optionally enable it for the verify_answer node and measure the difference as an experiment.
Model choice is configuration, and the final choice must be justified by the Day 4 benchmark.
